# Session 006 Learnings — Controller Container Architecture Pivot

**Date:** 2026-05-12
**Domain:** Bootstrap system / Controller container
**Session focus:** Part 02 (Schema) + Controller container implementation

---

## 1. Architecture Pivot: Bootstrap → Controller

**What we learned:** The original spec (bootstrap.py as host CLI) conflated two concepts: infrastructure provisioning and runtime governance. During implementation, it became clear that having a static bootstrap script that generates a compose file is too rigid for a dynamic agent system.

**What we changed:** Pivot to a single controller container that:
- Holds the Docker socket (secure, only one container has it)
- Exposes both CLI (user) and MCP (orchestrator) interfaces
- Dynamically manages agent lifecycle (provision/destroy)
- Maintains a JSON registry of running agents

**Key insight:** Governance is not an agent type — it's the controller itself. The original spec incorrectly listed `governance` in the agent type registry.

---

## 2. Volume Topology Evolution

**Original:** 2 volumes (project_vol + agent_vol)
**Current:** 4 volumes

Added:
- `{project}_flox_vol` — Shared Flox environment, mounted RO in agents. User installs packages via controller or host.
- `controller_state_vol` — Persistent JSON registry, compose history, backups.

**Rationale:** Separating Flox from project data allows environment updates without touching project code. Controller state needs persistence across restarts.

---

## 3. Compose File Strategy

**Options considered:**
1. Per-agent compose files with master `include:` — Rejected. Docker compose `include` creates service namespace collisions and makes removal complex.
2. Single master compose file, rewritten on changes — **Approved.** Simpler, predictable, no collisions.

**Implementation:** `ComposeGenerator.generate()` creates initial file. `add_agent()` appends service. `remove_agent()` deletes service + runs `docker compose stop/rm`.

## 4. Agent Type Registry Correction

**Spec error discovered:** `bootstrap-system-02-schema.md` §4 listed `governance` as an agent type with graph module, prompt, and skills.

**Correction:** Governance is the controller server. It does not get provisioned as an agent. Removed from:
- `defaults.json`
- `validators.py` `REGISTERED_TYPES`
- `docs/specs/bootstrap-system-02-schema.md`

Valid agent types: `orchestrator`, `system_thinker`, `implementer`, `auditor`, `explorer`, `memory_manager`.

---

## 5. MCP vs CLI Dual Interface

**Decision:** Controller exposes both:
- CLI (`agentctl`) for user via `docker exec`
- MCP tools for orchestrator via SSE

**Why both?** User needs direct control for debugging and manual operations. Orchestrator needs programmatic access for delegation. MCP is the standard protocol for agent-to-agent communication.

## 6. Registry Design

**Format:** JSON file (`/state/registry.json`)
**Structure:**
```json
{
  "projects": {
    "demo": {
      "agents": {
        "orchestrator": {
          "agent_key": "orchestrator",
          "agent_type": "orchestrator",
          "status": "running",
          "endpoint": "http://demo_orchestrator:8000",
          ...
        }
      },
      "compose_path": "/state/compose/docker-compose.demo.yml",
      "last_updated": "2026-05-12T..."
    }
  }
}
```

**Why JSON?** Simple, human-readable, no external DB dependency. SQLite was considered but rejected for MVP simplicity.

---

## 7. Docker SDK vs CLI Subprocess

**Decision:** Use `docker-py` SDK for volume/container operations, but `subprocess` for `docker compose` commands.

**Rationale:**
- SDK is clean for volume/container management
- `docker compose` CLI is the only reliable way to handle compose file parsing, network creation, and service orchestration
- `docker-py` does not have a compose API

---

## 8. Subpath Pre-Creation

**Constraint:** Docker `volume: subpath:` mounts require the subdirectory to exist in the volume before container creation.

**Solution:** Use alpine init containers at bootstrap/add-agent time:
```python
client.containers.run(
    image="alpine:latest",
    command=["sh", "-c", "mkdir -p /vol/{agent_key}/skills"],
    volumes={agent_vol: {"bind": "/vol", "mode": "rw"}},
    remove=True,
)
```

## 9. Model Regex Adjustment

**Issue:** Original regex `^[a-z_]+:[a-zA-Z0-9_.-]+$` rejected `opencode-go:deepseek-v4-pro` because provider name contains hyphens.

**Fix:** Updated to `^[a-z0-9_-]+:[a-zA-Z0-9_.-]+$` to allow hyphens in provider names.

## 10. What Was Left Out / Deferred

1. **Skills symlinks** — The original spec had complex symlink logic. Deferred because Deep Agents `skills=` parameter may be sufficient.
2. **System prompt files** — `system_prompt_file` field exists but loading logic is minimal. User said to ignore for now.
3. **Graph module strict validation** — `CompiledStateGraph` isinstance check requires langgraph import. Using duck-type check (`hasattr(graph, "invoke")`) to avoid hard dependency.
4. **Actual Docker testing** — No real Docker daemon was available during development. All Docker code is untested.

## 11. Open Questions for Future Sessions

1. **Controller self-creation** — How does the first controller container start? User will handle manually, but we need instructions.
2. **Agent base image** — `langgraph-agent-base:latest` is assumed. What packages does it need? User will build, but we need a spec.
3. **ACP transport between containers** — `deepagents-acp` only documents stdio. How does orchestrator connect to agent ACP over the Docker network? HTTP? SSE? Custom bridge?
4. **Port management** — If multiple controllers run (one per project), port 8000 conflicts. Should controllers use dynamic ports or a single shared controller for all projects?
5. **Flox activation** — How does the agent entrypoint activate Flox? `flox activate -- python entrypoint.py`? Does the base image need Flox installed?
6. **Controller restart recovery** — If controller container restarts, how does it reconcile running containers with registry state?
