# Learnings — Bootstrap System Spec (Session 2026-05-12)

## What I Was Asked to Do
Convert the existing `bootstrap_project.sh` bash script into a Python-based bootstrap
system. Then extend the design to cover the full pipeline: config schema, CLI, container
entrypoint, skills symlinking, and MCP proxying.

## Key Decisions Made

1. **Flat agent map config (not type registry + instances).** Simpler for MVP. No
   variations built yet. Regroup to registry+instances pattern when variations exist.

2. **manifest.json as intermediate artifact.** Bootstrap writes JSON; entrypoint reads
   JSON. Decouples bootstrap (host, Python, YAML, Docker SDK) from entrypoint
   (container, minimal deps, just json.loads).

3. **Skills symlinked at bootstrap time, not runtime.** Docker volumes RO for agents
   means runtime can't create symlinks. Bootstrap uses an alpine init container to
   create relative symlinks (`../../shared/skills/{name}`) that resolve correctly
   when both volumes are mounted in the running container.

4. **MCP endpoints: MVP uses direct URLs; governance proxy later.** The manifest schema
   supports both patterns — the URL field is just a string. MVP points to real servers
   (Qdrant, LiteLLM). When governance is built, manifest URLs change to governance
   proxy. No entrypoint code change needed.

5. **Tools separated: graph_tools + mcp_tools merged.** Graph modules that need custom
   tools expose `get_tools()`. MCP tools load via `MultiServerMCPClient.get_tools()`.
   Both are merged into `create_deep_agent(tools=[...])`.

6. **interrupt_on included from start.** It's a simple dict passthrough. Avoids config
   migration later when HITL becomes active.

7. **ACP transport for containers is an open question.** `deepagents-acp` docs only show
   stdio mode. Container transport (HTTP/SSE) needs further investigation. Spec flags
   this as unresolved.

## What I Assumed About the Existing System
- Docker SDK (`docker-py`) is acceptable (no subprocess calls to docker CLI).
- `langchain-mcp-adapters` `MultiServerMCPClient` supports both http and stdio transports.
- `create_deep_agent()` accepts `interrupt_on`, `permissions`, `skills`, `backend` as
  documented in the Deep Agents customization page.
- Graph modules follow the `get_graph() -> CompiledStateGraph` contract (confirmed for
  `src/memory/graph.py`, assumed for others).
- The `langgraph-agent-base` Docker image will include all needed Python packages
  (`deepagents`, `deepagents-acp`, `acp`, `langchain-mcp-adapters`, etc.).

## What I Was Uncertain About
- Whether `acp` package supports HTTP/SSE transport for containers (docs only show stdio).
- Whether `MultiServerMCPClient` needs to remain open (async context manager) or can be
  used as fire-and-forget after `get_tools()`. The docs show it being used inline without
  explicit cleanup, suggesting it handles its own lifecycle.
- The exact per-agent tools that each graph module will expose via `get_tools()` — only
  memory_manager has a concrete design so far.

## What I'd Do Differently Next Time
- Load framework skills (langchain-fundamentals, langgraph-fundamentals, deep-agents-core,
  deep-agents-orchestration, langchain-middleware) BEFORE starting the design, not after.
  The schema design needed confirmation that `create_deep_agent` accepts `interrupt_on`,
  `skills`, `permissions`, `backend` as parameters — this was confirmed by the
  customization page, but knowing it upfront would have streamlined the thinking.
- Investigate ACP transport options earlier. The container transport gap is a significant
  open question that affects the entrypoint design.
