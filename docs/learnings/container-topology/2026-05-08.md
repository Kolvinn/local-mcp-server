# Learnings — Container & Volume Topology Design

**Date:** 2026-05-08
**Task:** Design complete container, volume, and interaction topology for multi-container agent system.

## Key Decisions

1. **Symlink bridge pattern** (validated) — orchestrator mounts project-vol + all agent-vols, creates symlinks to grant file access. Zero copies, zero host access.
2. **One Dockerfile, all variations** — variation selected at runtime via VARIATION env var. Single Flox manifest covers all system tools.
3. **`.flox/run/bin` on PATH** — headless activation without `flox activate` overhead.
4. **Signal files for task dispatch** — file-based, no HTTP servers needed in agents.
5. **OpenCode headless on agents** — OpenCode provides skill loading, prompts, tools. LangGraph orchestrates.

## Uncertainties

- Can OpenCode run truly headless? Binary gate for entire architecture.
- Orchestrator user interaction model (CLI vs web vs MCP).
- Which model drives orchestrator reasoning in Approach A.

## What I'd Do Differently

- Test headless OpenCode before designing full architecture.
- Shorter spec — diagrams and schemas could be separate files.
